# Design: GitLab MCP Server

## Context

См. `proposal.md` для мотивации и бизнес-контекста. 

Проект разрабатывается с нуля на базе Node.js / TypeScript. Сервер взаимодействует с AI-ассистентами (Claude Code, Cursor, Claude Desktop) по протоколу MCP (Model Context Protocol) через стандартные потоки ввода-вывода (`stdio`). Сервер должен поддерживать работу как с облачным `gitlab.com`, так и с корпоративными self-hosted инстансами GitLab.

## Goals / Non-Goals

**Goals:**
- Модульная архитектура: изоляция инструментов по доменам (`mr`, `repository`, `ci`, `settings`, `discovery`) и их динамическая регистрация на основе флага `--tools`.
- Приоритетная иерархия конфигурации: возможность запускать несколько независимых копий сервера для разных инстансов/токенов через CLI-флаги или раздельные `.env` файлы.
- Контекстная оптимизация: агрегация связанных данных (MR + diff + threads + CI) в один вызов, очистка ANSI-кодов и обрезка хвостов логов для сохранения лимита токенов LLM.
- Безопасная работа с проектами: поддержка `project_id` как в виде чисел, так и путей `namespace/project-name` с опциональным проектом по умолчанию.

**Non-Goals:**
- Реализация транспортов HTTP / SSE на первом этапе (сервер работает исключительно через `stdio`).
- Покрытие всех существующих эндпоинтов GitLab REST API (реализуется только необходимый набор инструментов для разработки, ревью, CI и настройки репозитория).
- Локальное персистентное состояние или кеширование в СУБД (сервер остается stateless).

## Decisions

### 1. Библиотека для взаимодействия с GitLab API
- **Решение**: Использование `@gitbeaker/rest` (официальный и наиболее зрелый TypeScript SDK для GitLab API v4).
- **Обоснование**: Полная типизация эндпоинтов, встроенная обработка пагинации, поддержка кастомных хостов (`host` + `token`), автоматическое URL-кодирование путей с неймспейсами (`encodeURIComponent`).
- **Альтернативы**:
  - Нативный `fetch`: потребовалось бы писать вручную десятки DTO, обвязку пагинации и обработку ошибок.
  - `axios`: требует ручной типизации всех структур данных GitLab.

### 2. Загрузка конфигурации и CLI интерфейс
- **Решение**: Использование `commander` для парсинга CLI флагов и `dotenv` для работы с переменными окружения.
- **Обоснование**: `commander` обеспечивает стандартный POSIX CLI синтаксис (`--token`, `-t`, `--env-file`, `--tools`), генерирует `--help` и позволяет прозрачно объединять параметры командной строки с `process.env`.
- **Иерархия приоритетов**:
  1. CLI аргументы (`--url`, `--token`, `--tools`, `--default-project`, `--env-file`)
  2. Переменные окружения процесса (`GITLAB_API_URL`, `GITLAB_TOKEN`, `GITLAB_MCP_TOOLS`, `GITLAB_DEFAULT_PROJECT`)
  3. Файл `.env` (дефолтный или путь из `--env-file`)
  4. Жестко заданные дефолтные значения (URL: `https://gitlab.com/api/v4`, tools: `all`)

### 3. Модульная структура регистрации инструментов
- **Решение**: Каждый функциональный домен оформляется как изолированный модуль с интерфейсом регистрации:
  ```typescript
  interface ToolModule {
    name: 'mr' | 'repository' | 'ci' | 'settings' | 'discovery';
    register: (server: McpServer, client: GitbeakerClient, config: ServerConfig) => void;
  }
  ```
- **Обоснование**: Сервер регистрирует только те инструменты, чьи модули запрошены в параметре `tools`. Это защищает контекстное окно модели от раздувания и не позволяет вызывать административные методы, если модуль `settings` выключен.

### 4. Оптимизация контекста: обработка логов и диффов
- **Решение**: Использование библиотеки `strip-ansi` для очистки вывода логов GitLab CI от терминальных цветовых кодов и ограничение объема данных (хвост лога по умолчанию 200 строк; лимит диффа по умолчанию 500 строк).
- **Обоснование**: Неочищенный лог CI джобы содержит десятки тысяч строк с настройкой Docker-раннера и байтами ANSI-разметки, что способно мгновенно исчерпать контекстное окно модели.

### 5. Валидация входных данных инструментов через Zod
- **Решение**: Использование `zod` схем для описания аргументов каждого инструмента MCP.
- **Обоснование**: SDK MCP нативно транслирует Zod-схемы в JSON Schema, что дает ассистенту строгие подсказки по типам и обязательности параметров.

### 6. Комментирование строк кода в диффе (Inline Discussions)
- **Решение**: Инструмент комментирования кода принимает путь к файлу (`path`) и номер строки (`new_line` / `old_line`), а сервер самостоятельно запрашивает актуальные `diff_refs` (`base_sha`, `start_sha`, `head_sha`) из MR.
- **Обоснование**: Это освобождает LLM от необходимости вызывать низкоуровневые эндпоинты коммитов/диффов перед отправкой каждого замечания во время код-ревью.

## Risks / Trade-offs

- **[Большой объем изменений в MR]** → Автоматическое усечение диффа с признаком `diff_truncated: true` и возможностью запросить дифф конкретного файла через параметр `file_path`.
- **[Ограничения прав доступа токена (403 Forbidden)]** → Информативный перехват ошибок GitLab API с возвратом сообщения модели о недостаточных привилегиях токена для выполнения операции (например, при попытке защитить ветку токеном с правами Developer).
- **[Лимиты запросов GitLab API (429 Rate Limit)]** → Перехват ошибки с трансляцией заголовка `Retry-After` в ответ инструмента.
